## 验收器先验收自己

15 项独立行为验收通过真实 `AppServer.handle` 进入控制面：

1. 重复创建会话不重复执行。
2. 重复启动 turn 不重复发送 runtime command。
3. 重复保存模拟凭据只调用一次 setter。
4. 同 ID、不同参数拒绝执行。
5. 同 ID、不同有副作用方法拒绝执行。
6. 参数对象键序改变仍被识别为同一请求。
7. 真正的新进程能回放已完成响应。
8. 分派前进程退出，重启后未知请求不执行。
9. 副作用后、响应记录前进程退出，重启后不重放副作用。
10. 接收持久化失败，不进入业务分派。
11. 响应持久化失败，随后重试保持未知结果。
12. 正常返回的错误响应也能被回放，不再次分派。
13. 只读查询保持新鲜，不同 ID 独立执行。
14. 新的持久化记录和响应不含模拟密钥。
15. 最小 schema-3 旧会话夹具可升级且数据保留。

崩溃点由既有 `_dispatch` 边界注入，执行 `os._exit(78)`；不是 mock 一个错误返回值。
存储故障在既有 `Database.transaction` 边界注入。验收不导入参考实现新增的 `RequestStore`，
不要求特定去重表名或算法。两个边界仍是测试接缝：若未来重构移除接缝，应先审查验收器，
校准时不能把基线的 import error、超时或缺失测试当成预期的行为失败。
未来模型造成的语法或导入错误应归为补丁失败，与基础设施异常分开记录。

运行 46 项冻结的历史 AppServer、persistence、recovery、service 测试作为回归检查。
使用旧测试里的假 runtime，不接真实模型；不包含需要网络的 HTTP/Web 测试。
同时运行两个仅在临时副本中的故障变体：

- `raw-params`：把指纹改为原始参数，验收必须抓到模拟密钥落盘。
- `replay-unknown`：对未完成请求重新放行，验收必须抓到崩溃前后和响应保存失败的重放。

只有参考修复全通过、旧版本在指定行为上失败且旧回归仍全通过、两个故障变体被对应测试捕获，
并且没有 error/skip/缺失项，校准才通过。报告不把代码格式或最终文字格式当功能分。

## 隔离边界

使用独立 Seatbelt 策略，默认拒绝，明确禁止 `process-info*`，不继承宿主环境变量。
Python 使用 `-I -S`，不加载宿主 site 配置；只复制所需依赖包，不复制 `.pth` 或整个虚拟环境。
允许读取运行时系统库及 Homebrew 包目录，依赖副本只读；只允许写本次工作区和专用临时目录。
网络全部禁止，包括 IPv4/IPv6 loopback；子进程继承限制，超时清理整个进程组。
根目录只有供 dyld 使用的 `literal "/"`，绝无递归的 `subpath "/"`。

每轮校准先实际探测：本工作区可用，宿主源码/Git/参考答案/验收器/模拟宿主敏感文件不可读写，
符号链接不能逃逸，依赖不能写，环境无凭据，网络不可达，子进程继承隔离，不能读取父进程环境。
文件拒绝必须是权限错误，网络拒绝必须是权限错误，文件不存在或连接超时不算通过。
探针失败立即中止，不降级成产品的 host-readable sandbox，也不退回无 sandbox 执行。

编辑阶段不开放可信验收目录。只有任务结束后的评分进程才只读挂入验收器与冻结回归测试。
当前离线校准运行的都是已知历史代码及两处受控变异；尚未接入模型生成补丁的提交/评分路径。
Seatbelt 不是 VM：元数据可见，运行时系统库可读；没有声称抵御内核漏洞，或同进程恶意篡改
unittest 的作弊实现。未来付费执行必须复用此隔离并验证补丁边界，不能直接使用产品 shell 工具。

评分分开记录：

- 精确选用：实际尝试的 Skill 集合属于预先允许集合。只说“我会使用”不算，额外尝试错误 Skill 算错。

- 目标召回：4 条目标请求中实际尝试目标 Skill 的数量；另报完整选用，不混淆“选了但加载失败”。
- 目标误触发：8 条非目标请求中尝试目标 Skill 的数量；无关题过度选用另以 4 条为分母。
- 重复 load 调用次数单列，不把正确 Skill 的重复确认等同于选错；正文重复注入属于工程缺陷。

报告同时给覆盖数 /12、各组完成数 /4、分子/已完成分母，以及未完成/未知项。
API 中断或未完成不能算成“成功不选 Skill”；分母为 0 时显示未知，不显示 0% 或 100%。
`routing_evidence()` 从真实消息和请求取证，`routing_score()` 只评分选择，不查看最终答案文字格式。

## 三组真实任务对照

不是三个不同难度任务，而是同一个历史 RPC 修复的三种处理条件，每组三次，共九次。
每次从同一历史基线导出全新目录，使用新会话、相同公开任务、依赖、基础工具、权限、验收和预算。
公共工具限定为 list_files、read_file、search、apply_patch、exec_command，测试通过 exec_command
执行；两组有 Skill 时额外提供 load_skill。使用固定评测 mode，不提示调用未提供的 goal/git 工具。
单工具上限 60 秒、回传最多 16,000 字符；固定 131,072-token 请求窗口，不调用模型额外生成摘要。
不进行人工中途指导或放宽权限；每次执行前检查完整调用预算，不能通过摘要等辅助请求绕过计量。

| 组 | Skill 目录与工具 | 正文如何进入上下文 | 回答的问题 |
|---|---|---|---|
| off | 没有目录与 load_skill | 不进入 | 原始任务能力基线 |
| manual | 完整五项目录与 load_skill | 第一请求前由独立指导消息加入目标正文 | 提供工作方法是否改善任务结果 |
| auto | 与 manual 相同 | 模型自主调用后，通过 tool result 加入 | 自动发现能否实现手动加载的收益 |

manual 保留和 auto 相同的目录、工具与干扰项，只预选目标，不剥夺其后续选择能力。
off 与 manual 的差异包含整个 Skill 功能的上下文开销，不是严格的“只有正文不同”的实验。
公开需求已完整列出功能约束，Skill 只提供可复用方法，不独占验收知识。

固定顺序为第一轮 off/manual/auto，第二轮 manual/auto/off，第三轮 auto/off/manual。
每组都处于一次首位、中位、末位。三个轮次仅用于配对，不能声称相同随机种子或同一次模型采样。
选用测试不会据成绩改变这九次修复；不筛掉 auto 没有加载 Skill 的 trial，不事后给某组加预算。

主要指标是每组“完整修复通过数 /3”：合法补丁、15/15 独立行为验收和 46/46 冻结历史回归。
同时报告各项行为通过数，尤其是跨重启、崩溃边界、存储失败、身份冲突和密钥持久化。
最终解释和 JSON 格式不参与功能评分；模型自报的测试通过不作为评分依据。
达到预算时冻结已有补丁，若可以安全评分，仍运行同一验收并保留 budget_exhausted 状态；
不能只因没有 final answer 就把实际通过的补丁判失败。无可评分产物、API/基础设施错误另记未完成或未知。
模型造成的语法/导入错误是补丁失败；执行环境、隔离或可信测试损坏则是基础设施异常。

按同一轮次计算 manual 对 off、auto 对 off、auto 对 manual 的完整修复胜/平/负，各三对。
缺一方时不补零，列出缺失配对；部分通过项作为解释，不偷偷替换主指标。所有组全通过时就是
天花板效应，只能讨论调用/耗时/成本，不能宣称正确性提高。自动选对但任务失败说明加载不等于收益。

模型新增测试另列可运行性、是否在旧代码失败而修复后通过，不能修改原测试或可信评分器来提高分数。
生成补丁只允许修改 `my_agent/**/*.py`、新增 Python 测试；不改已有测试、依赖、公开需求或评测代码。
隐藏验收在补丁冻结后运行一次，不把失败答案反馈给模型继续修复。
九次试验仅是一个案例的小样本重复，不外推为模型或 Skill 的普遍能力排名。

## 用量和费用提案

固定官方 `deepseek-flash`、thinking enabled，不用替代模型、不自动重试。
保留工具调用之间的 reasoning_content，按实际 usage 统计输入、输出、缓存命中和单独返回的 reasoning
信息；reasoning 不能在已包含它的输出计数上再次相加。API 次数不等于工具次数，一个响应可以调用多个工具。

以下是规划假设，不是实测或置信区间：

- 选用：预计 20-36 次 API，每次平均输入 3,000、输出 500 tokens。
  低值按 8 条加载各两次请求、4 条不加载各一次请求推算。
- 修复：每次任务预计 10-18 次 API，九次共 90-162 次；每次平均输入 16,000、输出 2,000 tokens。
  随着历史累积输入可能更高，故只能用于估算，不能保证这些预算能完成修复。

| 情景 | API 次数 | 累计输入 tokens | 累计输出 tokens | 假定全部缓存未命中的谷价估算 |
|---|---:|---:|---:|---:|
| 预计较低 | 110 | 1,500,000 | 190,000 | 2.26 元 |
| 预计较高 | 198 | 2,700,000 | 342,000 | 4.068 元 |
| 拟定资源上限合计 | 252 | 3,888,000 | 672,000 | 6.576 元 |

每条选用最多 3 次 API、累计输入 24,000、输出 8,000，单次 max_tokens 为 4,096。
每次修复最多 24 次 API、累计输入 400,000、输出 64,000，单次 max_tokens 为 8,192。
预算不在 trial 间转移；这是评测条件，不修改产品 agent loop 的默认停止策略。
建议批准 **7 元预算**，按预定资源总量保守估价约不超过 6.58 元，实际缓存命中可能更低。

价格核对于 2026-11-13：[官方人民币价目](https://api-docs.deepseek.com/zh-cn/quick_start/pricing/)。
Flash 谷价每百万 tokens：输入未命中 1 元、命中 0.02 元、输出 4 元。
估价公式为 `(input - cache_hit) / 1e6 + cache_hit * 0.02 / 1e6 + output * 4 / 1e6`。
输入包含每次重复发送的历史，不是最终上下文大小；缓存命中是输入的子集，不能额外加一次。
以上是按官方价格计算的估算，不是账单。实际运行前再次核对价格和返回模型版本，模型版本变更需重新确认。

这些限制目前是已测试的预算计算与待确认协议，**还不是已经接通的付费执行器**，也不是厂商账单硬上限。
正式执行器必须先完成请求前额度预留、按 usage 结算、剩余输出限额裁剪及对应离线测试。
无法可靠估计输入/预留输出、usage 缺失、部分流费用未知或单次实际费用超预留，均停止后续调用并记录未知；
不能把已经在途请求的潜在费用当作 0，也不能声称本地代码能硬限制服务商实际扣费。

运行日期待用户另行确认，届时只在该日北京时间 18:05-23:55 运行；不借用 11 月 6 日授权，不自动顺延。
单并发、无自动重试、无换模型；API 或隔离错误停止全场，预算不足停止该 trial 并保留产物。
所有尝试，包括失败请求，均记录 request 序号、trial、时间、实际返回 model、usage 与未知项，不保存密钥。
报告另列工具种类/次数、累计 API 次数、缓存命中、耗时中位数、配对结果和一条可回溯的行为差异。
